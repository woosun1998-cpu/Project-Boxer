# 03. 복서(Boxer) 프로젝트 모듈화 전략 및 계획

이 문서는 현재 구조(정적 HTML/JS 프론트 + FastAPI 백엔드)를 전제로, **모듈화를 바라보는 관점**과 **실행 가능한 통합 계획**을 정리한 것이다.

---

## 1. 관점별 요약 (Boxer에 맞게 해석)

### 1) Layered Architecture (계층형)

**핵심:** UI → 애플리케이션(유스케이스) → 도메인 → 인프라(DB·외부 API)로 의존 방향을 한쪽으로 고정한다.

- **백엔드:** `routers`(HTTP) → `services`(유스케이스) → `models/schemas`(도메인·계약) → `database`/외부 클라이언트(인프라).
- **프론트:** `pages`(또는 라우트 단위) → `features`(기능 단위 로직) → `core`(API·인증) → `shared`(UI 유틸).

**Boxer에 유리한 점:** 이미 `routers` / `services` 패턴이 있으므로, **서비스 경계를 “기능 단위”로 명확히** 나누기 좋다.

---

### 2) AOP (Aspect-Oriented Programming, 관점 지향)

**핵심:** “비즈니스 로직”과 “횡단 관심사(cross-cutting)”를 분리한다. (로깅, 인증/인가, 메트릭, 트랜잭션, 레이트 리밋 등)

- **FastAPI에서는:** 의존성 주입(`Depends`), 미들웨어, 라우터 레벨 데코레이터/공통 의존성으로 AOP에 가깝게 구현한다.
- **프론트(바닐라 JS)에서는:** `api.js` 래퍼, 공통 에러 처리, 토스트, 인증 헤더 삽입이 사실상 횡단 관심사에 해당한다.

**Boxer에 유리한 점:** 인증·CORS·에러 응답 형식 `{ success, data }` 등 **한곳에 모이게** 두면 기능 추가 시 중복이 줄어든다.

---

### 3) FSD (Feature-Sliced Design)

**핵심:** “페이지”가 아니라 **기능(feature)**을 슬라이스 단위로 묶는다. (`features/auth`, `features/tutorial`, `features/sparring` …)

- 레이어 예: `app` → `pages` → `widgets` → `features` → `entities` → `shared` (프로젝트 규모에 따라 일부만 채택 가능).
- **바닐라 HTML**에서는 폴더를 `js/features/diet/`, `js/features/tutorial/`처럼 나누고, 페이지는 얇게 유지하는 방식이 현실적이다.

**Boxer에 유리한 점:** `tutorial`, `sparring`, `diet`, `admin`처럼 **사용자 여정이 다른 영역**을 물리적으로 분리하기 좋다.

---

### 4) Clean Architecture (클린 아키텍처)

**핵심:** “비즈니스 규칙”이 프레임워크·DB·HTTP에 의존하지 않도록 **안쪽 원**에 두고, 바깥은 어댑터로 둔다.

- **유스케이스:** “튜토리얼 완료 처리”, “세션 종료”, “다이어트 측정 결과 저장” 같은 **앱이 하는 일**을 문장으로 정의.
- **인터페이스(포트):** 저장소·AI 클라이언트를 추상화하고, **구현(어댑터)**은 `app/infrastructure` 또는 `repositories`에 둔다.

**Boxer에 유리한 점:** 나중에 DB를 바꾸거나 Gemini 호출 방식을 바꿔도 **도메인 규칙**을 덜 건드리게 할 수 있다. 다만 **소규모 팀/초기 단계**에서는 전 계층에 클린을 100% 적용하면 과투자가 될 수 있으므로, **핵심 도메인(세션·랭킹·과금)**부터만 엄격히 적용하는 점진 전략이 맞다.

---

## 2. 관점 종합: Boxer에 맞는 원칙 5가지

| 원칙 | 설명 |
|------|------|
| **경계는 “기능” 기준** | 튜토리얼/스파링/다이어트/관리자는 서로 다른 변경 주기 → FSD식 feature 경계. |
| **HTTP는 얇게** | 라우터는 DTO 검증·위임만, 규칙은 service/domain 쪽 (Layered + Clean의 일부). |
| **횡단 관심사는 한곳** | 인증, 로깅, 공통 에러, API 래퍼 (AOP에 해당). |
| **의존 방향 안쪽** | 도메인 규칙은 DB/SDK에 직접 의존하지 않도록 포트/어댑터는 “필요할 때” 도입 (Clean). |
| **프론트는 점진적** | 바닐라 유지 시 `js/features/*` + `js/shared/*`부터; 번들러 도입은 후속 단계. |

---

## 3. 통합 모듈화 계획 (단계별)

### Phase 0 — 현 상태 정리 (선행)

- **백엔드:** `routers` ↔ `services` ↔ `models` 의존 관계 다이어그램 1장 정도로 문서화.
- **프론트:** `js/core`(api, auth) vs 페이지별 인라인 스크립트 혼재 여부 파악, **공통만 `shared`로 이동** 후보 목록 작성.

**산출물:** `docs/architecture-overview.md` 수준의 짧은 메모 (선택).

---

### Phase 1 — 백엔드: 계층 정리 + 횡단 관심사 통일 (Layered + AOP)

1. **라우터:** 요청/응답 스키마 검증 + `service` 호출만 담당.
2. **서비스:** 유스케이스 단위 파일 (`tutorial_service`, `session_service` 등) 유지·분리.
3. **공통:**
   - 인증/권한(관리자 등)은 `Depends`로 일원화.
   - 응답 포맷·예외 핸들러는 한곳에서 처리(가능하면).
4. **DB 접근:** `repositories/` 또는 `services` 내부 private 함수로 쿼리 응집도 높이기 (과도한 추상화는 금지).

**완료 기준:** 새 API 추가 시 “라우터에 SQL이 없고, 서비스에만 비즈니스가 있다”가 기본이 된다.

---

### Phase 2 — 프론트: FSD에 가까운 폴더 구조 (기능 슬라이스)

목표 디렉터리 예시 (점진 적용):

```
frontend/js/
  core/           # API, auth (기존 유지)
  shared/         # toast, dom 유틸, 상수
  features/
    tutorial/     # TutorialEngine 연동, 튜토리얼 전용 UI 로직
    sparring/     # HitboxJudge, 게임 루프 연결
    diet/         # 캠 모드, localStorage, 피드백 번역
    admin/        # 관리자 전용 폼·테이블
```

- **HTML**은 가능하면 “얇게”: 스크립트는 `type="module"`로 `features/*` 진입점만 로드하는 방향을 검토 (브라우저 지원·빌드 없이도 가능).
- **우선순위:** 새로 추가한 `diet`·`admin` 관련 JS부터 `features`로 옮기기 쉬움.

**완료 기준:** 기능별로 JS 파일을 찾을 때 `features/<이름>/`만 보면 된다.

---

### Phase 3 — 클린 아키텍처 “핵심만” (도메인·포트)

다음 영역부터 **유스케이스 + 포트(인터페이스)**를 도입 검토:

- **세션/라운드/랭킹 점수 규칙** (비즈니스 규칙이 모이는 곳)
- **결제/티어/코인** (도입 시 반드시 경계 필요)
- **AI 코칭(Gemini)** — 외부 API는 어댑터로 격리

**완료 기준:** “DB 테이블 이름”이나 “HTTP 상세”가 유스케이스 서술에 섞이지 않도록 리뷰 가능.

---

### Phase 4 — 운영·품질 (모듈화의 마무리)

- **관측:** 로깅 구조화, 주요 유스케이스별 트레이스 ID (선택).
- **테스트:** 서비스 단위 단위 테스트 우선, 라우터는 통합 테스트 소수.
- **배포:** Docker/nginx로 프론트·API 분리는 이미 문서에 있음 → 환경 변수·시크릿은 절대 코드에 없음 유지.

---

## 4. 리스크 및 현실적인 타협

| 리스크 | 대응 |
|--------|------|
| 바닐라 + 거대 HTML | 모듈 분리는 `features` 폴더와 진입 JS부터; 빌드 도입은 필요 시점에. |
| 과도한 추상화 | Clean의 “포트/어댑터”는 결제·외부 API처럼 **변경 비용이 큰 경계**에만. |
| 팀 규모 | 문서·리뷰 기준(라우터 얇게)부터 합의가 우선. |

---

## 5. 한 줄 결론

**Layered로 백엔드 뼈대를 고정하고, FSD로 프론트를 기능 단위로 쪼개며, AOP에 가까운 방식으로 인증·에러·API 래퍼를 한곳에 모으고, 비즈니스 핵심(세션·랭킹·과금·외부 AI)에만 Clean Architecture의 포트/어댑터를 점진 적용**하는 것이 Boxer에 가장 균형 잡힌 모듈화 전략이다.
